Ticket System — Master Feature Catalog (complete)

This is the definitive Domainify ticket / helpdesk product catalog.
Update status in place only (done / partial / blank). Do not split into parallel lists.
KB product details live in kb-features.txt; this file lists ticket-KB touchpoints only.

Product assumption: authenticated Domainify customers talk to support staff; UI locales en / fa / ar / tr (RTL where needed); Domainify context (domains, marketplace, SMS.ir, wallet) is a first-class differentiator.

A. TICKET MODEL AND LIFECYCLE
------------------------------------------------------------------------------

1. Identity and create
done - Create ticket (subject, description, category, priority, attachments)
done - Auto-generate unique public ticket ID (e.g. TCK-2026-000142)
done - Channel stamp at create (portal today; email / SMS / chat / social later)
done - Link ticket to authenticated user account
done - Guest / unauthenticated ticket create (optional; email verification required)
done - Linking guest tickets to a User after later registration.
done - add CAPTCHA to guest tickets page
done - Guest list of all their tickets (single-token-per-ticket only).
done - Clone / duplicate ticket as new
done - Proactive / outbound ticket opened by agent on behalf of customer
done - Import tickets from CSV / other helpdesk (migration)
SSR SEO pages, full public Help Center ticket widget.

2. Classification
done - Priority levels: Low / Medium / High / Urgent (admin-configurable labels)
done - Categories / types (admin-configurable; e.g. Billing, Technical, Domains, SMS, Account, Other)
done - Tags / labels (multi-select; predefined + free-form)
Priority matrix (impact x urgency -> computed priority)
Severity / urgency as separate fields (incident-style)
Service / product area taxonomy (Domains, Marketplace, SMS, Wallet, Account)
Source / intake type (bug, question, request, complaint, abuse)

3. Status and workflow

done - Configurable status labels, sort order, and allowed transitions (fixed status codes)
done - Reopen closed tickets (within configurable time window)
Custom status codes beyond the fixed enum (full status designer) — later / optional
Spam / junk status or dedicated junk queue with bulk discard
Awaiting third-party status (registrar, payment gateway, SMS provider)

4. Structure and relations

Parent / child hierarchy (incident / problem -> many customer tickets)
Tasks / checklist items on a ticket
Follow-up / reminder date separate from SLA due
Snooze (hide from inbox until datetime; auto-return)
Bookmark / star for agent personal list

5. Closure quality
done - Internal notes vs public replies (customers never see internal notes)
Resolution / close reason codes (required on resolve/close; admin-configurable)
Resolution summary field (customer-visible or internal)
First-contact resolution flag (auto or manual)
Prevent close without public reply / resolution code (policy)
